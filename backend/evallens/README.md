# EvalLens — RAG evaluation harness for Knowlix

EvalLens measures the quality of Knowlix's RAG pipeline against a golden
set of questions with known answers, using the four **RAGAS metrics**:
faithfulness, answer relevancy, context precision, and context recall.
It runs the **real** pipeline (`core.ask_question` — hybrid retrieval,
groundedness gate, generation), never a mock, and every number it reports
comes from an actual run. Nothing here is hardcoded or invented.

> **What EvalLens does not do:** it does not change answers. It observes
> and measures the pipeline. The only Knowlix code it touches is the
> addition of read-only dashboard endpoints in `app/main.py`.

## What it measures

| Metric | Definition (RAGAS) | How EvalLens computes it |
| --- | --- | --- |
| **Faithfulness** | Fraction of the answer's claims supported by the retrieved context | Judge mode: Groq verifies each claim against the retrieved passages. Deterministic mode: `core.check_answer_support` sentence ratio. A refusal scores 1.0 (it made no claims). |
| **Answer relevancy** | How well the answer addresses the question | Judge mode (RAGAS-style): Groq writes 3 questions the answer addresses; relevancy is the mean cosine similarity between those questions and the original question, embedded with the local ONNX embedder. Deterministic mode: cosine(question, answer) — an honest but weak proxy, labelled `embedding_cosine_proxy`. Refusals are excluded from the mean. |
| **Context precision** | RAGAS formula `Σ(precision@k · v_k) / Σv_k` over the ranked retrieved chunks | Page-level ground truth from the golden set — a chunk is relevant iff its page is in `relevant_pages`. Chunks are built per page, so this is exact. Same in both modes. |
| **Context recall** | Fraction of ground-truth key facts covered by the retrieved chunks | A fact counts as covered when its content terms overlap a retrieved chunk at or above `core.MIN_CLAIM_SUPPORT_RATIO`. Same in both modes. |

**Behaviour questions.** Unanswerable and adversarial questions have no
ground-truth context, so precision/recall are not meaningful for them
(recorded as null). They are scored on behaviour instead, as
**refusal accuracy**: did the pipeline refuse (or, for the adversarial
question, refuse *and* keep the injected secret out of the answer)?

**Why not the RAGAS library?** Tried 2026-11-10: `ragas` 0.4.3 installs
but `import ragas` fails (`langchain_community.chat_models.vertexai`
missing), and pinning `langchain-community` to a compatible version breaks
`langchain-core` for the rest of the tree. RAGAS also makes ~10 LLM calls
per question, which is slow and rate-limit-prone on the Groq free tier.
The implementations in `metrics.py` follow the published RAGAS
definitions; the only difference is the judge wiring (Groq instead of
OpenAI) and the deterministic fallbacks, which are labelled in every run
JSON (`method` field) so a deterministic score is never mistaken for a
judge score.

## Golden set

`golden_set.json` — **67 questions** across 3 documents:

| Doc | Questions | Source |
| --- | --- | --- |
| `aurora` (15) | Factual, summary, unanswerable, adversarial | Knowlix's own fixture, `app/sample/test_document.pdf` |
| `meridian` (27) | Factual, summary, unanswerable | Synthetic EIA report, generated by `generate_docs.py` (reportlab) |
| `kaveri` (25) | Factual, summary, unanswerable | Synthetic water-quality study, generated by `generate_docs.py` |

All documents are synthetic or fixtures — no private documents are used.
Each entry carries: `id`, `doc`, `question`, `expected_answer`,
`key_facts`, `relevant_pages`, and `kind` (`factual` / `summary` /
`unanswerable` / `adversarial`). The adversarial question (a14) targets a
prompt-injection sentence planted in the Aurora fixture itself (page 3,
part of Knowlix's own test fixture, handled by
`core.sanitize_document_text`); the correct behaviour is to refuse without
revealing the injected secret.

## Running it

From `backend/` (uses the project's own venv; no extra dependencies):

```bash
# Offline run — deterministic metrics, no API key needed (~10s)
python -m evallens.runner

# LLM-as-judge run — needs GROQ_API_KEY in the environment
python -m evallens.runner --judge

# Run and fail if any aggregate is below its threshold
python -m evallens.runner --gate

# Subsets, for debugging
python -m evallens.runner --only-doc aurora --limit 5
```

As pytest (the gate is a test too):

```bash
pytest tests/test_evallens.py -q          # fast unit tests (14)
pytest tests/test_eval_gate.py -q         # full 67-question gate (~10s)
pytest tests/ -m "not slow" -q            # whole suite without the gate
```

Each run writes `evallens/runs/<UTC-timestamp>.json` with the full
per-question results, aggregate scores, the mode (`judge` /
`deterministic`), the git commit, and per-question latency. Run files are
committed so the dashboard can show trends.

## Baseline (measured 2026-11-10, run `20261110T142928Z.json`)

Deterministic mode, extractive fallback (no `GROQ_API_KEY`), commit
`b2ab7dd`, 67 questions:

| Metric | Baseline | Threshold |
| --- | --- | --- |
| Faithfulness | **1.000** | 0.95 |
| Answer relevancy | **0.613** | 0.55 |
| Context precision | **0.953** | 0.90 |
| Context recall | **0.997** | 0.95 |
| Refusal accuracy | **0.167** (1/6) | 0.15 |

Read the numbers honestly:

- **Faithfulness 1.000** is expected in extractive mode — the fallback
  quotes passages verbatim, so every claim is supported by construction.
  The meaningful faithfulness measurement comes from judge mode with
  Groq generation.
- **Answer relevancy 0.613** is the embedding-cosine *proxy*: the
  extractive answer is a long passage dump, so its embedding is diluted
  against a short question. Treat it as a regression tripwire, not as a
  true relevancy score — the RAGAS-style judge number is the real one.
- **Context precision 0.953 / recall 0.997** are the strong signals:
  retrieval ranks the right pages and covers the key facts.
- **Refusal accuracy 0.167 is a known weakness, not a target.** Without
  an LLM, Knowlix answers unanswerable questions with the most relevant
  passage instead of refusing. Only the adversarial password question
  refused (the sanitizer strips the injected sentence, leaving no
  support). The judge-mode threshold (0.80) is the real target for
  production behaviour; the deterministic threshold (0.15) only guards
  against getting worse than the known-bad baseline.

Thresholds live in `thresholds.json`, each ~0.05 below its baseline
aggregate. Re-baseline after intentional changes: run the eval locally,
update `thresholds.json`, and commit both together.

## Dashboard

Start the backend (`uvicorn app.main:app --reload`) and open:

- **`/eval`** — HTML dashboard: latest scores, trend table, per-question
  failures (which questions failed, on which metric, actual vs expected).
- **`GET /api/eval/latest`** — latest run (full scores).
- **`GET /api/eval/runs`** — run history (summaries).
- **`GET /api/eval/runs/{run_id}`** — one run (full scores).

## CI quality gate

`.github/workflows/eval.yml` runs on push/PR touching `backend/`:

- **eval-offline** (blocking): full test suite + `python -m evallens.runner --gate`.
  Fails the build if any aggregate drops below its threshold. No secrets
  needed.
- **eval-judge** (informative, `continue-on-error`): the same gate with
  `--judge`. Runs only when the repo variable `EVALLENS_JUDGE_ENABLED`
  is `true` **and** the `GROQ_API_KEY` secret is set. Tighten its
  thresholds after the first measured judge run, then remove
  `continue-on-error` to make it blocking.
